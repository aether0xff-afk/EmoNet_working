# Ruca/Rookie 프로젝트 통합 설계 문서 v0.1

## 프로젝트 한 줄 정의

Ruca/Rookie 프로젝트는 감정 trace, 내부 목소리, 관계 기억, 다중 캐릭터 역할 구조를 결합해 사용자의 요청에 반응할 뿐 아니라 상황에 따라 스스로 해석하고 움직이는 캐릭터형 상호작용 시스템이다.

## 전체 목표

이 문서는 Ruca/Rookie 프로젝트의 핵심 개념을 공유 가능한 보고서 형태로 정리하면서, 이후 MVP 구현자가 바로 모듈 경계와 데이터 흐름을 이해할 수 있도록 개발 명세의 기본 단위를 함께 정의한다.

기존 EmoNet 계열의 핵심 관점인 "감정은 단순 라벨이 아니라 시간에 따라 변화하는 내부 상태 trace"라는 전제를 유지한다. 다만 Ruca/Rookie/Ricky/Rocky 구조는 Luca 계열 MVP의 단순 캐릭터 응답 실험을 확장한 차세대 설계로 본다. 이 설계의 중심은 하나의 답변을 생성하는 모델이 아니라, 여러 내부 역할이 감정과 기억을 바탕으로 상호 조정하며 최종 반응을 만드는 시스템이다.

---

## 1. 프로젝트 개요

### 개념 설명

Ruca/Rookie 프로젝트는 캐릭터가 사용자의 입력을 단순히 해석하고 답하는 구조를 넘어서, 입력 전후의 감정 변화, 관계 기억, 내부 판단, 자발적 반응 가능성을 함께 다루는 상호작용 구조다.

Ruca는 중심 상호작용 캐릭터이며, Rookie는 사용자 또는 초입자/관찰자 포지션의 성장형 캐릭터다. Ricky와 Rocky는 Ruca 내부 또는 주변 시스템에서 판단, 균형, 추진력, 방어 에너지를 담당하는 보조 역할로 작동한다.

### 시스템 의미

이 프로젝트의 목적은 "말투가 있는 챗봇"을 만드는 것이 아니라, 지속적인 관계와 감정 흐름을 가진 캐릭터 시스템을 만드는 것이다. 따라서 핵심 상태는 단일 응답이 아니라 다음 요소들의 조합이다.

- 현재 감정 trace
- 사용자와의 관계 기억
- 캐릭터별 역할과 성향
- 내부 목소리 후보
- 자발 반응 트리거
- 최종 응답에 반영되는 감정적 선택

### 구현 관점

초기 MVP는 하나의 완전한 인격 시뮬레이터를 목표로 하지 않는다. 우선 캐릭터 프로필, 감정 상태, 메모리, 내부 목소리, 자발 반응 판단, 응답 조합기를 분리해 구현한다. 각 모듈은 독립적으로 테스트 가능해야 하며, 전체 시스템은 텍스트 입력을 받아 상태를 갱신하고 최종 응답을 생성하는 파이프라인으로 시작한다.

## 2. 전체 시스템 구조

### 개념 설명

전체 시스템은 사용자 입력을 받아 감정 상태와 기억을 갱신하고, 여러 내부 목소리 후보를 생성한 뒤, Ruca의 중심 응답으로 정리하는 흐름을 가진다. 필요할 경우 사용자의 직접 질문이 없어도 자발 반응을 생성할 수 있다.

기본 흐름은 다음과 같다.

```text
User Event
  -> Context Analyzer
  -> MemoryStore
  -> EmotionState
  -> InnerVoiceEngine
  -> SpontaneousReactionEngine
  -> ResponseComposer
  -> Ruca Response
```

### 시스템 의미

이 구조에서 감정은 응답을 꾸미는 후처리 요소가 아니다. 감정 trace는 내부 목소리 후보의 우선순위, 자발 반응 여부, 말투의 강도, 기억 저장 방식에 직접 영향을 준다.

MemoryStore는 단순 대화 로그가 아니라 관계적 의미를 저장하는 계층이다. 예를 들어 사용자가 반복해서 불안을 표현했는지, 특정 캐릭터에게 더 자주 기대는지, Ruca가 이전에 어떤 약속이나 반응을 남겼는지를 별도 상태로 유지한다.

### 구현 관점

초기 구현에서는 다음 순서로 처리한다.

1. 사용자 입력과 최근 대화 맥락을 분석한다.
2. 관련 단기 기억과 장기 기억을 조회한다.
3. 감정 trace를 갱신한다.
4. Ruca, Ricky, Rocky 관점의 내부 목소리 후보를 생성한다.
5. 자발 반응이 필요한지 판단한다.
6. 최종 응답을 Ruca의 말투와 관계 상태에 맞춰 구성한다.

## 3. Ruca / Rookie / Ricky / Rocky 역할 정의

### 개념 설명

이 프로젝트의 다중 캐릭터 구조는 단순히 여러 인물이 번갈아 말하는 방식이 아니다. 각 캐릭터는 시스템 안에서 서로 다른 기능적 역할을 가진다.

| 이름 | 기본 정의 | 핵심 기능 |
| --- | --- | --- |
| Ruca | 중심 상호작용 캐릭터 | 사용자와 직접 관계를 맺고 최종 반응을 표현한다. |
| Rookie | 사용자 또는 초입자/관찰자 포지션의 성장형 캐릭터 | 낯섦, 배움, 적응, 관계 형성의 관점을 담당한다. |
| Ricky | 판단, 해석, 균형 조정 역할 | 상황을 분석하고 과잉 반응을 조정하며 의미를 정리한다. |
| Rocky | 추진력, 방어, 행동 에너지 역할 | 위기 반응, 결단, 보호, 행동 개시의 압력을 만든다. |

### 시스템 의미

Ruca는 외부에 보이는 중심 캐릭터지만, Ruca의 반응은 단독으로 만들어지지 않는다. Ricky는 해석과 균형을 제공하고, Rocky는 에너지와 방어적 긴장을 제공한다. Rookie는 사용자의 위치를 비추는 성장형 관점으로, 사용자가 시스템 안에서 어떻게 낯섦을 지나 관계로 들어오는지 설명하는 역할을 한다.

### 구현 관점

초기 MVP에서 모든 캐릭터가 독립 응답자로 말할 필요는 없다. 우선 각 캐릭터를 `CharacterProfile`로 정의하고, 내부 목소리 후보 생성 시 역할별 관점을 반영한다. 최종 출력은 기본적으로 Ruca가 담당하되, 필요하면 응답 내부에 Ricky식 판단이나 Rocky식 추진력이 섞일 수 있다.

## 4. Ruca 자발 반응 시스템

### 개념 설명

Ruca 자발 반응 시스템은 사용자가 직접 질문하지 않아도, 감정 상태나 관계 기억이 특정 조건에 도달했을 때 Ruca가 먼저 말을 걸거나 반응하는 구조다.

자발 반응은 임의의 랜덤 이벤트가 아니라 다음 조건을 바탕으로 판단된다.

- 사용자의 최근 감정 신호가 강하게 누적된 경우
- 이전 대화에서 남은 약속, 미완료 주제, 걱정 요소가 있는 경우
- 긴 침묵 이후 관계적 연결을 회복할 필요가 있는 경우
- 내부 목소리 간 긴장이 커져 최종 표현이 필요해진 경우
- Ruca의 성향상 그냥 지나치기 어려운 사건이 감지된 경우

### 시스템 의미

자발 반응은 캐릭터가 살아 있는 듯한 느낌을 만드는 핵심 요소다. 다만 사용자의 주도권을 빼앗지 않아야 하므로, MVP에서는 낮은 빈도와 명확한 조건을 가진 반응부터 시작한다.

### 구현 관점

`SpontaneousReactionEngine`은 현재 감정 trace, 최근 이벤트, 기억 상태, 캐릭터 성향을 입력으로 받아 다음 값을 반환한다.

- `should_react`: 자발 반응 여부
- `reaction_type`: 걱정, 확인, 제안, 회상, 장난, 침묵 유지 등
- `intensity`: 반응 강도
- `reason`: 반응이 발생한 내부 이유

초기 버전에서는 사용자가 입력한 직후 "추가 자발 반응을 붙일지" 판단하는 방식으로 시작한다. 완전한 백그라운드 알림이나 시간 기반 자동 발화는 후속 단계로 둔다.

## 5. 내부 목소리 구조

### 개념 설명

내부 목소리는 최종 응답 이전에 생성되는 여러 해석과 반응 후보를 뜻한다. Ruca는 사용자의 입력에 즉시 하나의 답을 내는 대신, Ricky식 해석, Rocky식 방어/추진, Ruca식 관계 반응을 내부적으로 비교한다.

### 시스템 의미

내부 목소리 구조는 캐릭터 반응에 깊이를 만든다. 예를 들어 같은 사용자 입력이라도 Ricky는 "상황을 더 정확히 확인하자"고 말할 수 있고, Rocky는 "지금 바로 움직이자"고 압력을 만들 수 있다. Ruca는 이 둘을 그대로 노출하지 않고 관계와 말투에 맞춰 최종 응답으로 조율한다.

### 구현 관점

`InnerVoiceEngine`은 최소 세 종류의 후보를 만든다.

- `ruca_voice`: 관계 중심의 감정 반응
- `ricky_voice`: 분석, 해석, 균형 조정
- `rocky_voice`: 보호, 행동, 추진력

각 후보는 다음 필드를 가진다.

```text
voice_id
source_character
content
emotion_bias
urgency
confidence
recommended_action
```

최종 응답에는 모든 내부 목소리를 그대로 표시하지 않는다. `ResponseComposer`가 현재 상황에 맞는 후보를 선택하거나 섞어 Ruca의 한 문장 또는 여러 문단으로 변환한다.

## 6. 감정 학습 방식

### 개념 설명

감정 학습은 사용자의 말을 특정 감정 라벨 하나로 분류하는 것이 아니라, 시간에 따라 변하는 내부 trace를 갱신하는 방식으로 설계한다. 감정은 현재 입력, 이전 기억, 캐릭터 성향, 관계 상태가 함께 만든다.

### 시스템 의미

Ruca의 감정은 "기쁨", "불안", "분노" 같은 단일 태그가 아니라, 여러 축의 변화량과 잔향으로 표현된다. 이 방식은 기존 EmoNet의 trace-as-emotion 관점을 이어받는다. 감정 trace는 말투와 응답 선택뿐 아니라 어떤 기억을 더 강하게 저장할지도 결정한다.

### 구현 관점

`EmotionState`는 MVP에서 다음 상태를 가진다.

- `valence`: 긍정/부정 방향
- `arousal`: 각성 또는 긴장 수준
- `affinity`: 사용자에 대한 친밀도 또는 접근성
- `stability`: 감정 안정도
- `protective_tension`: 보호/방어 긴장
- `curiosity`: 관심과 탐색 욕구

각 입력 후 `EmotionState`는 이전 상태와 입력 분석 결과를 바탕으로 갱신된다. 초기에 복잡한 학습 모델을 쓰지 않더라도, 규칙 기반 업데이트와 로그 저장으로 시작할 수 있다.

## 7. 메모리 시스템

### 개념 설명

메모리 시스템은 대화 로그를 저장하는 계층을 넘어, 관계적으로 중요한 사건과 감정 변화를 구조화해 저장한다. Ruca가 사용자를 기억한다는 느낌은 단순히 과거 문장을 재인용하는 것이 아니라, 어떤 사건이 어떤 감정 흔적을 남겼는지를 반영할 때 생긴다.

### 시스템 의미

메모리는 다음 세 층으로 나눈다.

- 단기 기억: 현재 세션의 최근 대화와 즉시 참조할 맥락
- 장기 기억: 반복되는 사용자 성향, 선호, 중요한 사건
- 관계 기억: Ruca와 사용자 사이의 약속, 친밀도, 갈등, 회복 경험

### 구현 관점

`MemoryStore`는 MVP에서 JSON 또는 경량 로컬 저장소로 시작할 수 있다. 각 기억 항목은 다음 정보를 포함한다.

```text
memory_id
memory_type
summary
source_event
emotion_snapshot
importance
last_accessed_at
created_at
```

초기 구현에서는 자동 저장 규칙을 단순화한다. 감정 강도가 높거나, 사용자가 명시적으로 중요하다고 말했거나, 이후 대화에 영향을 줄 가능성이 높은 정보만 장기 기억으로 승격한다.

## 8. 다중 캐릭터 구조

### 개념 설명

다중 캐릭터 구조는 Ruca, Rookie, Ricky, Rocky가 각각 독립된 인격처럼 작동할 가능성을 열어두되, MVP에서는 역할 기반 내부 시스템으로 시작한다. 즉 외부에는 Ruca가 주로 말하고, 내부에는 여러 관점이 존재한다.

### 시스템 의미

이 구조는 두 가지 장점을 가진다. 첫째, Ruca의 반응이 단순한 말투 모방이 아니라 내부 갈등과 조정의 결과처럼 보인다. 둘째, 이후 별도 모드에서 Ricky나 Rocky가 직접 발화하는 확장도 가능하다.

### 구현 관점

각 캐릭터는 `CharacterProfile`로 정의한다.

```text
character_id
name
role
traits
tone_style
relationship_state
visibility
```

`visibility`는 해당 캐릭터가 외부에 직접 말할 수 있는지, 내부 목소리로만 쓰이는지를 구분한다. MVP 기본값은 Ruca만 외부 발화 가능, Ricky와 Rocky는 내부 목소리, Rookie는 사용자/성장 관점 모델로 둔다.

## 9. Zeta식 스토리텔링에서 가져올 점

### 개념 설명

Zeta식 스토리텔링에서 가져올 핵심은 캐릭터가 단순히 정보를 전달하는 것이 아니라, 관계의 장면과 감정의 흐름 안에서 반응한다는 점이다. 즉 사건보다 반응의 결이 중요하고, 설정 설명보다 관계 변화가 중요하다.

### 시스템 의미

Ruca/Rookie 프로젝트는 Zeta식 장면감을 다음 방식으로 반영한다.

- 응답이 항상 정보 전달로만 끝나지 않도록 한다.
- 캐릭터가 사용자의 상태를 장면 속 신호처럼 해석한다.
- 이전 대화의 정서적 잔향이 다음 반응에 남도록 한다.
- 캐릭터의 말투가 상황에 따라 미세하게 변한다.
- 침묵, 망설임, 조심스러운 확인 같은 비정보성 반응도 의미 있게 다룬다.

### 구현 관점

초기 구현에서는 별도 스토리 엔진을 만들지 않는다. 대신 `ResponseComposer`가 감정 trace와 기억을 바탕으로 응답의 장면감을 조절한다. 예를 들어 같은 조언이라도, 사용자가 지친 상태라면 짧고 부드럽게, 결단이 필요한 상태라면 더 단단하게 구성한다.

---

## 10. 구현 모듈 제안

### 개념 설명

MVP는 시스템을 작게 나누고, 각 모듈이 입력과 출력을 명확히 갖도록 설계한다. 이 문서에서 제안하는 최소 모듈은 다음과 같다.

### 시스템 의미

| 모듈 | 책임 |
| --- | --- |
| `CharacterProfile` | 캐릭터별 성향, 역할, 말투, 관계 상태를 정의한다. |
| `EmotionState` | 현재 감정 trace와 변화량을 저장하고 갱신한다. |
| `InnerVoiceEngine` | 내부 목소리 후보를 생성하고 충돌 가능성을 표시한다. |
| `MemoryStore` | 단기 기억, 장기 기억, 관계 기억을 저장하고 조회한다. |
| `SpontaneousReactionEngine` | 사용자의 직접 요청 없이 반응할 필요가 있는지 판단한다. |
| `ResponseComposer` | 내부 목소리와 감정 상태를 Ruca의 최종 응답으로 구성한다. |

### 구현 관점

초기 데이터 흐름은 다음 인터페이스를 기준으로 둔다.

```text
input_event
  -> context_summary
  -> memory_hits
  -> emotion_state_next
  -> inner_voice_candidates
  -> spontaneous_reaction_decision
  -> final_response
```

초기에는 모든 모듈이 같은 프로세스 안에서 동작해도 된다. 중요한 것은 모듈의 책임을 섞지 않는 것이다. 예를 들어 `MemoryStore`는 응답 문장을 만들지 않고, `ResponseComposer`는 장기 기억 저장 여부를 직접 결정하지 않는다.

## 11. 현재까지 채택된 결정

### 개념 설명

현재 설계에서 채택된 결정은 다음과 같다.

- Ruca는 중심 상호작용 캐릭터다.
- Rookie는 사용자 또는 초입자/관찰자 포지션의 성장형 캐릭터다.
- Ricky는 판단, 해석, 균형 조정을 담당한다.
- Rocky는 추진력, 방어, 행동 에너지를 담당한다.
- 감정은 라벨이 아니라 trace로 다룬다.
- 내부 목소리는 최종 응답 이전의 조정 구조로 둔다.
- 자발 반응은 무작위가 아니라 상태 기반으로 판단한다.
- MVP에서는 Ruca가 주로 외부 발화를 담당한다.
- 메모리는 단기, 장기, 관계 기억으로 분리한다.

### 시스템 의미

이 결정들은 프로젝트의 방향을 "캐릭터 말투 생성"이 아니라 "감정과 기억을 가진 관계형 캐릭터 시스템"으로 고정한다.

### 구현 관점

개발자는 MVP에서 모든 기능을 완성하려 하기보다, 위 결정들이 깨지지 않도록 최소 기능을 구현해야 한다. 특히 감정 trace, 내부 목소리, 관계 기억은 이름만 남기지 말고 실제 상태로 저장되어야 한다.

## 12. 미정 / 추가 논의 필요

### 개념 설명

다음 항목은 MVP 이후 또는 구현 직전 추가 결정이 필요하다.

- Rookie가 실제 별도 캐릭터로 발화할지, 사용자 포지션 모델로만 남을지
- Ricky와 Rocky가 외부 대화에 직접 등장할 수 있는 조건
- 자발 반응의 빈도 제한과 사용자 제어 방식
- 감정 trace의 축 개수와 세부 업데이트 공식
- 장기 기억 저장 시 사용자 확인이 필요한 범위
- 캐릭터 간 충돌이 강할 때 최종 응답을 고르는 방식
- Zeta식 장면감을 어느 정도까지 응답에 드러낼지

### 시스템 의미

이 항목들은 캐릭터의 생동감과 사용자 부담 사이의 균형에 직접 영향을 준다. 특히 자발 반응과 장기 기억은 사용자가 불편함을 느끼지 않도록 명확한 제어권을 제공해야 한다.

### 구현 관점

MVP에서는 불확실한 항목을 과도하게 자동화하지 않는다. 직접 발화 캐릭터는 Ruca로 제한하고, 자발 반응은 낮은 빈도와 명확한 이유를 가진 경우로 제한한다. 장기 기억은 중요도 기준을 낮게 잡지 않고, 명시적 신호가 있는 경우부터 저장한다.

## 13. MVP 구현 방향

### 개념 설명

MVP의 목표는 완전한 다중 캐릭터 세계관 구현이 아니라, Ruca가 감정 trace와 기억, 내부 목소리를 바탕으로 일관된 반응을 생성하는 최소 시스템을 만드는 것이다.

### 시스템 의미

첫 MVP는 다음 질문에 답할 수 있어야 한다.

- 각 캐릭터가 무엇을 담당하는가?
- 자발 반응은 언제 발생하는가?
- 내부 목소리는 최종 응답에 어떻게 반영되는가?
- 감정 학습과 메모리는 어떤 상태를 저장하는가?
- 첫 MVP에서 반드시 구현할 모듈은 무엇인가?

### 구현 관점

MVP의 최소 범위는 다음과 같다.

1. `CharacterProfile`로 Ruca, Rookie, Ricky, Rocky를 정의한다.
2. `EmotionState`로 입력 전후 감정 trace를 저장한다.
3. `MemoryStore`로 최근 대화와 중요 관계 기억을 저장한다.
4. `InnerVoiceEngine`으로 Ruca, Ricky, Rocky 관점의 내부 후보를 만든다.
5. `SpontaneousReactionEngine`으로 추가 반응 필요 여부를 판단한다.
6. `ResponseComposer`로 Ruca의 최종 응답을 만든다.
7. 각 단계의 중간 상태를 디버그 로그로 확인할 수 있게 한다.

MVP 완료 기준은 단순히 응답이 생성되는 것이 아니다. 같은 입력이라도 감정 상태와 기억이 달라지면 내부 목소리 후보와 최종 응답이 달라져야 한다. 또한 자발 반응이 발생한 경우, 시스템은 그 이유를 사람이 읽을 수 있는 형태로 남겨야 한다.
