## 전체 흐름 요약

이번 대화 히스토리는 크게 다섯 단계로 나뉜다.

- 1단계는 `v3` 구현 착수 단계였다. 사용자가 EmoNet v1의 최종 명세를 매우 세세하게 고정했고, 그에 맞춰 그래프 기반 감정 시뮬레이터와 CLI, 기본 검증 구조가 잡혔다.
- 2단계는 구현 점검과 end-to-end 검증 단계였다. `text -> stim_vec -> EmoNet -> z -> s_pred -> response` 흐름이 실제로 이어지는지 확인했고, 여기서 “감정은 입력 텍스트에서 다시 추론하는 것이 아니라 `z` 또는 `z`의 히스토리에서 읽어야 한다”는 중요한 설계 원칙이 강화됐다.
- 3단계는 논문화와 외부 전달 준비 단계였다. 논문 개요, 기술 본문, 이관 문서, 데이터 번들, 최신 draft 점검이 이어졌고, `v3`를 논문 기준 최신 구현으로 취급하는 해석이 명확해졌다.
- 4단계는 연구 실패 지점의 구조적 보정 단계였다. direct baseline보다 약한 결과, 응답의 과도한 온화함, dominant branch 길이 붕괴, judge 파이프라인 불안정성, 원격 실행 환경 불일치가 핵심 문제로 떠올랐다.
- 5단계는 branch dynamics 심화 연구 단계였다. 단순 프롬프트 보정이 아니라 branch 길이, 점화 조건, max tick, 파라미터 sweep, trace 분석, 자동 최적화로 연구 초점을 이동시켰고, “순수성”을 유지하면서도 더 긴 사고 흐름을 만드는 방향으로 정리가 진행됐다.

### 2026-03-25 | `v3` 구현 명세 확정과 1차 구현 시작

스레드: `Implement EmoNet v1 spec`

목표: 사용자가 EmoNet v1의 계산 구조를 애매함 없이 고정하고, 곧바로 코딩 가능한 수준으로 닫는 것.

핵심 결정:
- 뉴런 수는 256개로 고정했다.
- 타입 비율은 inhibitory 45%, excitatory 45%, modulatory 10%로 유지했다.
- `fire_j = K_j`를 코드 규약으로 고정했다.
- modulatory dropout은 전체 뉴런이 아니라 “현재 깨어 있는 뉴런 집합”에만 적용하는 것으로 수정했다.
- dominant branch는 실시간 path 저장이 아니라 `branch_log`를 tick별 그래프로 남긴 뒤, 종료 후 survivor를 역추적해 복원하는 구조로 정리했다.
- 파이프라인은 `text -> stim_vec -> graph simulation -> dominant_branch -> z -> s -> LLM response`로 확정했다.

성과:
- `v3/emonet/core.py`와 `v3/emonet/cli.py` 중심으로 시뮬레이터 골격이 구현됐다.
- `v3/tests/test_emonet_smoke.py` 기반의 기본 스모크 검증 구조가 생겼다.
- `z` 대량 생성까지는 완료됐지만, 당시 시점에서는 `s` 회귀 학습이 아직 완전히 붙지 않았다는 점이 명시됐다.
- 세션 말미에는 32축 데이터셋 구축이 다음 우선 과제로 떠올랐다.

남은 과제:
- `z -> s` 학습 체인을 안정화해야 했다.
- LLM subset 라벨링 결과를 더 키워야 했다.
- 다음 세션으로 넘길 수 있는 구현 요약이 필요했다.

### 2026-03-27 | end-to-end 검증과 감정 해석 주체 재정의

스레드: `v3 end-to-end 워크플로 검증`

목표: `v3`가 실제로 전체 파이프라인을 끝까지 수행할 수 있는지 검증 절차와 통과 기준을 세우는 것.

초기 검증 범위:
- `text -> stim_vec -> EmoNet -> z`
- `z -> s_pred`
- `s_pred + input_text -> LLM response`
- 로그 및 산출물 저장

중간 전환:
- 단순 “올인원 테스트 가능 여부”를 넘어서, `z`가 연구에서 무엇을 뜻하는지에 대한 개념 논의가 시작됐다.
- 여기서 가장 중요한 설계 수정이 나왔다. 감정은 입력 텍스트에서 다시 읽어서는 안 되고, EmoNet이 만든 `z` 또는 `z`의 시간 히스토리에서 읽어야 한다는 점이다.

핵심 결론:
- 구조는 `input_text -> EmoNet -> z/history -> LLM emotion interpretation -> response`로 이해하는 것이 더 타당하다.
- 단일 시점 `z`보다 최근 `z`의 변화량과 흐름이 중요하므로, 향후에는 히스토리 기반 감정 정의가 필요하다고 정리됐다.

의미:
- 이 세션은 단순 검증 세션이 아니라, EmoNet을 “감정 생성 엔진”으로 보고 LLM을 “그 상태의 해석 및 표현기”로 두는 이론적 전환점이었다.

### 2026-04-03 이후 대형 세션 | 성능 저하, 온화함 편향, branch dynamics 문제를 한꺼번에 다룬 핵심 연구 구간

스레드: `감정 제어 LLM 연구계획서 작성`

이 세션은 사실상 가장 긴 메인 연구 로그였다. 시작은 논문 초안과 차트 배치 보강이었지만, 곧 direct baseline보다도 못한 성능 문제 때문에 연구의 중심이 “논문 문장 다듬기”에서 “왜 시스템이 실패하는가를 구조적으로 고치기”로 이동했다.

#### 1. 논문 강화와 원격 대형 데이터 생성

초기 목표:
- 차트와 그래프를 적절한 위치에 배치할 수 있게 논문 본문을 더 논문답게 강화
- 성능을 높일 방법 탐색
- 원격 RDP 환경에서 큰 데이터를 뽑아 오기

실제 진전:
- 원격 환경 기준 명령어가 준비됐고, `extended40` 계열 데이터 생성이 진행됐다.
- 사용자는 `out_z_training_extended40.csv` 51,628행 생성 완료 로그를 전달했다.
- 이후 “필요한 데이터는 다 얻은 건가?”라는 질문이 나오면서, 연구에 쓰인 산출물과 과거 파일 정리 필요성이 커졌다.

#### 2. 파일 정리, 아카이브, 최신 draft 감사

중간 목표:
- 과거 파일은 완전히 삭제하지 말고 히스토리를 남긴 채 아카이브
- 최신 draft를 현재 데이터에 맞게 다시 점검
- 실패하거나 부족한 부분을 정리하고 해결책 제시

핵심 문제 정리:
- 논문이 현재 결과를 그대로 쓰면 “연구가 실패한 것처럼 보이는 상태”
- 응답은 여전히 부드러움 쪽에 과도하게 치우침
- dominant branch 길이 분포에서 L1 비중이 너무 높음

이 시점의 방향 전환:
- 단순한 문장 보정이 아니라, branch collapse와 softening bias를 분리해서 다뤄야 한다는 인식이 명확해졌다.

#### 3. branchfix와 anti-softening rule

사용자 반응:
- “좋아 고쳐”
- “branch 길이도 1이 가장 많잖아 그 문제도 해결해야 해”

연구 조치:
- branch 길이 문제를 줄이기 위한 `branchfix` 계열 결과를 확인했다.
- `anti-softening prompt rule`을 추가해, 감정 표현이 과도하게 완화되는 경향을 줄이려 했다.

중간 관찰:
- branchfix 적용 후 branch 길이 통계가 개선되는 징후가 있었지만, 사용자는 “아직 브랜치가 너무 짧다”고 판단했다.
- 따라서 prompt rule만으로는 충분하지 않고, 내부 동역학을 건드려야 한다는 결론으로 이동했다.

#### 4. 파라미터 sweep, 진행률/ETA 요구, 원격 실행 루프 정착

사용자 요구:
- 파라미터를 계속 바꿔 가면서 그래프로 보고 판단하자
- 모든 코드에 진행률과 ETA를 표시해 달라
- 시간 오래 드는 본 실행은 RDP에서 돌리고, 여기서는 작은 smoke를 먼저 확인해 달라

의미:
- 연구 방식이 “단발 수정”에서 “실험 자동화 + 장시간 원격 실행 + 결과 피드백 루프” 형태로 바뀌었다.
- 이후 parameter sweep, optimization, smoke test, full run의 구조가 자리잡았다.

#### 5. LLM judge 실패 분석과 GPT-5.4 테스트

문제:
- LLM judge 결과가 휴리스틱으로 때워서는 안 되는 수준으로 불안정했다.
- 사용자는 “휴리스틱을 하지 말고 LLM judge가 안된 이유를 분석해”라고 요구했다.

진전:
- GPT-OSS 외에 GPT-5.4 judge 가능성도 검토됐다.
- 사용자는 로컬 한정 사용을 전제로 API 키를 제공했고, assistant는 로컬 경로에서 judge를 시험했다.
- 결과적으로 judge 파이프라인 문제는 모델 종류보다 prompt/format 안정성 문제에 더 가깝다는 흐름이 형성됐다.

의미:
- 이 구간은 “평가 체계 자체의 신뢰도”를 연구의 한 축으로 보게 만든 계기였다.

#### 6. 순수성 회귀와 branch dynamics 연구로의 전환

후반 핵심 논점:
- 사용자는 “너무 튜닝하려고 하지 말고 날것 그대로를 보자”고 선을 그었다.
- 또 “브랜치 길이 60 자체가 너무 짧다”며, 조기 붕괴를 일으키는 노드 알고리즘을 의심했다.
- 점차 “프롬프트 보정”보다 “그래프 내부 사고 흐름을 더 오래 유지하게 하는 법”이 핵심 과제가 됐다.

사용자 방향 제시:
- 제한을 굳이 40에 묶지 말 것
- 에러는 줄이고 CPU를 최대한 활용할 것
- 가능하면 보정 대신 파라미터 조정 또는 뉴런 기능 확장으로 갈 것
- 순수성을 해치는 과도한 보정은 지양할 것

이 구간에서 생긴 연구 방향:
- ignition 제거 혹은 완화
- `max_ticks` 확대
- pure branch dynamics 구성 실험
- trace 분석과 auto optimization 도구 도입

대표 산출물 흐름:
- branch sweep 결과
- branch optimize 결과
- trace analysis 결과
- branch dynamics research 보고서

#### 7. trace 분석과 자동 최적화

말미 문제의식:
- 전체 파라미터 조정만으로는 한계가 있으니, trace를 한번 분석해 원인을 더 직접 보자는 제안이 나왔다.
- 동시에 “한번에 파라미터를 자동으로 최적화하는 도구”가 필요하다는 요구도 명확해졌다.

결과:
- branch dynamics를 분석하는 스크립트와 최적화 스크립트가 연구 중심 도구로 올라왔다.
- 사용자는 smoke에서 개선된 수치를 보고, 이어서 full run과 더 큰 범위 실험으로 넘어가도록 요청했다.
- 그러나 끝까지 “보정이 많은 성공”보다 “순수한 구조에서 얻는 설득력 있는 개선”을 더 중요하게 보는 태도가 유지됐다.

정리:
- 이 대형 세션은 EmoNet 연구의 성격을 바꿨다.
- 처음에는 “논문 잘 쓰기”와 “성능 조금 올리기”가 목적이었지만, 끝에서는 “branch collapse의 구조적 원인을 분석하고, 더 깊은 감정 사고 흐름을 만드는 방법”이 중심 문제가 되었다.

## 누적 핵심 결론

- EmoNet 연구의 중심 축은 일관되게 “감정을 외부 라벨이 아니라 내부 상태 생성 과정으로 다루는 구조”였다.
- 구현 초기에는 `z` 생성기 구축이 중심이었고, 이후에는 `z`를 어떻게 해석하고 표현할지, 더 나아가 `z`가 충분히 길고 깊은 동역학을 갖도록 만들 수 있는지가 핵심으로 옮겨갔다.
- LLM 응답의 과도한 온화함은 단순 문체 문제가 아니라, prompt 구성과 내부 state 활용 방식이 함께 얽힌 구조적 문제로 다뤄졌다.
- dominant branch 길이 붕괴는 연구 전체에서 가장 반복적으로 제기된 실패 신호였으며, 이후 파라미터 sweep, branchfix, pure dynamics, trace 분석으로 이어지는 핵심 동인이 됐다.
- 논문화 작업은 구현과 별개가 아니라, 실제로는 실험 부족, 재현성 부족, 평가 설계 미흡을 발견하고 보완하는 연구 운영 장치로 작동했다.
