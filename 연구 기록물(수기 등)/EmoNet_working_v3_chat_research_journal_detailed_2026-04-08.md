## 3. 연구 전체 흐름 한눈에 보기

전체 채팅 히스토리를 연구 단계로 다시 묶으면 다음과 같다.

### 3.1 1단계: 설계 닫기와 초기 구현

이 단계의 핵심 질문은 “EmoNet v1을 애매함 없이 코드로 옮길 수 있느냐”였다.

- 출력 구조를 `stim_vec`, `dominant_branch`, `z`, `s`로 고정했다.
- 뉴런 수, 뉴런 타입 비율, tick 수, branch 추출 방식 등 애매한 부분을 사용자 쪽에서 매우 강하게 닫았다.
- `fire_j = K_j` 같은 용어 규약이 확정됐다.
- 아직 논문 서사보다 구현 일관성이 우선이었다.

### 3.2 2단계: 파이프라인이 실제로 끝까지 이어지는지 검증

이 단계의 핵심 질문은 “`text -> stim -> z -> s -> response`가 말이 아니라 실제 흐름으로 작동하느냐”였다.

- `e2e-check`와 스모크 테스트 구조가 정리됐다.
- `z`가 실제 감정 상태의 중심 표현인지, `s`가 그 표현을 잘 반영하는지 논의가 시작됐다.
- 여기서 결정적으로 “감정은 입력 텍스트를 다시 읽어 추론하면 안 된다. EmoNet이 만든 `z`나 `z` 히스토리에서 읽어야 한다”는 원칙이 세워졌다.

### 3.3 3단계: 논문화와 외부 전달 준비

이 단계의 핵심 질문은 “지금까지의 구현을 논문, 이관 문서, 데이터 번들로 바꿀 수 있느냐”였다.

- `MIGRATION_FOR_WRITER_AI.md` 같은 이관 문서가 만들어졌다.
- 논문 개요와 기술 본문이 여러 번 다시 작성됐다.
- requested table, data bundle, paper metrics snapshot 등 논문용 정리 산출물이 준비됐다.

### 3.4 4단계: 실패 양상 확인과 구조적 병목 파악

이 단계의 핵심 질문은 “왜 direct baseline보다 못하고, 왜 응답이 너무 부드럽고, 왜 branch가 짧게 죽느냐”였다.

- softening bias가 핵심 문제로 부각됐다.
- dominant branch length가 지나치게 1로 쏠린다는 문제가 반복적으로 제기됐다.
- 원격 실행 환경과 로컬 최신 코드가 어긋나 있는 운영 문제도 함께 드러났다.

### 3.5 5단계: branch dynamics와 trace 중심의 심화 연구

이 단계의 핵심 질문은 “파라미터와 구조를 조정해 더 깊고 설득력 있는 감정 동역학을 만들 수 있느냐”였다.

- 단순 프롬프트 조절보다 branch dynamics, ignition, max tick, late ignition, runaway persistence가 더 중요한 변수로 떠올랐다.
- optimizer, branch analysis, trace analysis 같은 연구 도구가 새 중심축이 됐다.
- 사용자는 “순수성”을 강조하며, 과도한 보정보다 구조적 설명력이 높은 방향을 선호했다.

## 4.1 2026-03-25 | `Implement EmoNet v1 spec`

세션 ID: `019d2481-e730-7f03-915c-4937f23503f8`

작업 경로: `C:\Users\esl01\OneDrive\문서\GitHub\EmoNet_working\v3`

세션 성격: “아이디어 설명”이 아니라, 바로 코딩 가능한 수준으로 명세를 닫는 구현 세션

### 당시 배경

사용자는 이 세션 초반에 EmoNet v1을 “기본값까지 임의 결정해서 닫는다”는 식으로 제시했다. 이 말은 곧, 이후에 코드를 짤 때 논쟁하거나 해석 여지를 남기지 말고 바로 구현으로 들어가라는 뜻이었다.

초기 명세에서 강조된 것은 다음과 같았다.

- 입력은 `text`
- 중간 출력은 `stim_vec`, `dominant_branch`, `z`, `s`
- 최종적으로는 `s`만 LLM에 전달
- 뉴런 수는 256개
- inhibitory / excitatory / modulatory 비율 고정
- base `stim_vec`는 tick마다 동일 공급
- 변화는 memory 및 타입 효과에서 발생
- branch는 tick 로그를 저장한 뒤 종료 후 복원

### 대화 전개

이 세션에서 가장 중요한 전환은 assistant가 명세를 요약한 뒤, 사용자가 세 군데를 다시 바로잡은 부분이었다.

사용자 수정 1:
- modulatory dropout은 “전체 뉴런”이 아니라 “현재 깨어 있는 뉴런 집합”에만 적용되어야 한다.

사용자 수정 2:
- `inputK`는 단순한 “이웃 K 평균”이 아니라, 더 정확히는 이웃의 발화 강도 평균이다.
- 그리고 v1에서는 이를 `fire_j = K_j`로 통일한다.

사용자 수정 3:
- dominant branch는 실시간 path object들을 저장하는 방식이 아니다.
- 먼저 tick별 `branch_log`를 저장하고, 종료 후 survivor를 역추적해서 path를 복원한 뒤, top-k mixture를 만든다.

이 수정은 단순한 표현 교정이 아니었다. 이후 `core.py`의 구현 방향, branch reconstruction 해석, 실험 결과를 읽는 방식 모두에 직접 영향을 주는 결정이었다.

### 이 세션에서 굳어진 핵심 원칙

- `fire_j = K_j`는 단순 편의가 아니라 v1 구현 규약이다.
- branch는 실시간 object가 아니라 사후 복원되는 경로다.
- modulatory dropout은 awake subset에만 적용된다.
- 파이프라인은 `text -> stim_vec -> graph simulation -> dominant_branch -> z -> s -> response`로 고정한다.

### 구현과 검증 쪽에서 실제로 오간 내용

세션 중반 이후에는 단순 명세 대화에서 벗어나 실제 실행 여부가 오갔다.

- 사용자는 benchmark 결과와 ridge encoder 관련 파일을 언급하며 인코더 쪽 상태를 확인했다.
- unit test 실행 중에는 잘못된 경로에서 테스트를 돌리다 수정하는 과정이 있었다.
- `v3/tests` 기준 테스트가 돌아가는지, `some_input.csv`를 통해 실제 입력 테스트가 가능한지 확인하려는 흐름이 보였다.

이 흐름으로 보아, 이 세션은 “종이 위 명세”와 “실제 구동 가능 코드” 사이를 처음 연결한 날이었다.

### 세션 말미 상태

세션 마지막 무렵 사용자 관심사는 두 갈래로 갈라졌다.

- 지금까지 구현한 것을 정리해야 한다.
- 다음 세션에서 32축 데이터셋 작업을 시작해야 한다.

assistant의 마지막 정리는 대체로 이런 상태를 말해준다.

- `v3/emonet/core.py`, `v3/emonet/cli.py`, `v3/tests/test_emonet_smoke.py`가 현재 핵심 구현 위치다.

- 하지만 당시 시점에는 `s` 회귀 학습이 아직 완전히 닫히지 않았다.

- 원격 실행 시 경로/입력 파일 문제는 어떻게 해결하는가

사용자 메시지 중에는 `FileNotFoundError`와 원격 경로 차이에 대한 내용도 있었다. 이것은 단순 요약 요청 뒤에 실제 운영 이슈가 이미 따라붙고 있었음을 보여준다.

### 이 세션의 실질적 역할

1. 구현 상태를 사람이 이해 가능한 말로 재정리했다.
2. 사용자가 직접 실행해야 할 명령어와 절차를 묻는 흐름이 생겼다.
3. 가장 중요하게는, “이제 구현과 검증을 한 세션에 섞지 말고 분리하자”는 결론이 나왔다.

### 왜 검증 분리 결정이 중요했는가

assistant는 세션 말미에 새 채팅에서 검증을 따로 하자고 제안했다. 그 이유는 다음과 같았다.

- 지금 스레드는 이미 구현 기록이 너무 길다.
- 이제부터는 “무엇을 만들었는가”보다 “실제로 제대로 동작하는가”가 중요하다.
- 목적이 다른 작업을 한 스레드에 계속 쌓으면 이후 기록으로서도 읽기 어려워진다.

이 판단은 이후 `v3 end-to-end 워크플로 검증` 세션으로 직접 이어졌다.

### 이 세션이 남긴 과제

- end-to-end 검증을 전용 세션에서 수행
- `z -> s` 체인과 실제 응답 생성의 연결 점검
- 원격/로컬 실행 명령 체계 표준화

## 4.4 2026-03-27 | `v3 end-to-end 워크플로 검증`

세션 ID: `019d2ee7-8be8-74c0-9fa8-aa62b9ec1aa1`

작업 경로: `v3`

세션 성격: 기능 검증 세션으로 시작했으나, 감정 표현의 주체를 다시 정의하는 설계 전환점이 된 세션

### 출발 질문

사용자는 검증 범위를 처음부터 아주 명확하게 적었다.

- `text -> stim_vec -> EmoNet -> z`
- `z -> s_pred`
- `s_pred + input_text -> LLM response`
- 로그/산출물 저장

즉, 추상적 “잘 되냐”가 아니라, 파이프라인 각 단계별로 실제 실행 가능한 검증 절차와 통과 기준, 실패 원인 분류까지 원했다.

### 중간에 드러난 핵심 불만

검증이 진행되면서 사용자는 “왜 계속 완만하냐”, “`z` 자체는 문제 없는 거냐”, “`s`를 어떻게 처리하는 게 좋으냐”는 질문으로 옮겨 갔다. 이 질문은 단순 성능 불만이 아니라, EmoNet에서 감정이 어디에 존재하는지에 대한 문제였다.

그 흐름에서 사용자는 매우 중요한 말을 했다.

- 입력 텍스트를 기반으로 LLM 응답을 바꾸는 것이 본질이 아니다.
- EmoNet 감정 엔진이 느낀 감정을 응답에 녹여내는 것이 중요하다.
- 따라서 LLM은 입력이 아니라 `z` 혹은 `z`의 흐름을 보고 감정을 정의해야 한다.

### 이 세션의 이론적 전환

이 세션 이후 EmoNet 파이프라인은 단순히 이렇게 읽히지 않게 되었다.

- 입력 텍스트를 읽어 감정을 알아낸 뒤, 적당히 응답을 만든다

대신 이렇게 읽히게 됐다.

- 입력 텍스트는 감정 엔진의 자극 입력이다.
- EmoNet은 내부 상태 `z` 또는 `z` 히스토리를 만든다.
- LLM은 그 내부 상태를 읽어 현재 감정을 정의하고, 그 정의된 감정을 응답에 반영한다.

이 전환은 나중에 논문 초록과 본문, migration 문서, softening bias 분석의 토대가 된다.

### 이 세션이 남긴 과제

- `z` 단일 시점보다 `z/history`를 다루는 설계 보강
- `s`가 정말 필요한 중간 단계인지, 혹은 LLM이 직접 `z/history`를 읽는 방식이 더 나은지 검토
- 검증 도구를 단순 동작 확인에서 “감정 전달 실패 원인 분석”까지 확장

### 4.13.7 softening bias와 branch collapse를 두 개의 독립 병목으로 분리

사용자는 응답이 지나치게 부드럽고, branch 길이는 대부분 1이라며 두 문제를 동시에 강조했다. 이때 중요한 것은 assistant가 둘을 한 문제로 뭉개지 않았다는 점이다.

- softening bias는 응답 표현과 prompt 전달 문제
- branch collapse는 동역학과 branch 추출 구조 문제

이 분리는 매우 중요했다. 왜냐하면 이후 연구가 “prompt 문구 조금 수정”에 머물지 않고, branch dynamics 자체를 별도 분석 대상으로 끌어올렸기 때문이다.

### 4.13.8 branchfix, 기본 dynamics 완화, CLI 파라미터 노출

assistant는 branch collapse 문제를 줄이기 위해 dynamics 기본값과 branch scoring을 수정하는 방향으로 갔다.

대화 흐름상 핵심 조치는 다음과 같았다.

- threshold, decay, refractory, memory mix, dropout/prune/rewire 기본값 조정
- `min_ticks_before_converged` 같은 조기 수렴 억제 장치 도입
- dominant branch scoring에 길이 친화 요소 반영
- branch 관련 파라미터를 CLI 옵션으로 노출해 sweep 가능하게 함

사용자는 단순 “좋아졌다”가 아니라 실제 branch 길이 통계를 요구했고, assistant는 평균 길이, `len1` 비율, 최대 길이 등을 비교 근거로 제시했다.

### 4.13.9 branchfix 이후의 새로운 문제: 다시 라벨링할 것인가

branchfix 적용 후에는 개선 조짐이 있었지만, 새 문제도 생겼다.

- 4000개를 다시 라벨링하면 너무 오래 걸린다
- branchfix 검증에 정말 full re-labeling이 필요한가

assistant는 여기서 “가장 싼 검증 경로”를 택했다. 기존 `extended40` 라벨 데이터를 재활용할 수 있는지 검토하고, 필요한 경우에만 새 라벨링을 하자고 정리했다.

이 판단은 연구 운영 측면에서 의미가 컸다. 불필요한 대형 실행을 줄이지 않으면 branch dynamics 연구를 제대로 밀어붙일 시간이 사라지기 때문이다.

### 4.13.10 `L1 collapse`에서 `late ignition`으로 진단 중심이 이동

branch 길이 문제를 더 들여다보자, assistant는 “짧은 branch”보다 더 근본적인 패턴이 `late ignition`일 수 있다고 보기 시작했다.

핵심 관찰은 다음과 같았다.

- 초반에 한참 비활성 상태로 있다가
- 늦게 점화되고
- 그 뒤에는 거의 포화 상태로 끝까지 간다

즉, branch가 짧게 죽는 문제와 늦게 켜지는 문제, 그리고 켜진 뒤 너무 오래 가는 문제가 한 축으로 연결되어 있었다.

이 지점에서 assistant는 `analyze_branch_dynamics.py`를 중심으로 결과를 표와 히스토그램으로 남기기 시작했다.

### 4.13.11 ignition 제거, `max_ticks` 상향, 순수성 회귀

이 시점의 사용자 태도는 분명했다.

- 너무 많이 튜닝하지 말라
- 날것 그대로를 보고 싶다
- 보정이 많으면 프롬프팅과 다를 바 없어진다
- 초기 설계에서 너무 멀어지면 안 된다

이에 따라 assistant는 다음과 같은 방향을 택했다.

- `ignition` 제거
- 기본 `max_ticks`를 `40 -> 128`로 상향
- CLI와 연구 스크립트에서도 ignition 관련 옵션 정리

이 단계의 아이러니는, branch collapse를 막았더니 이제는 반대로 너무 오래 살아남는, 즉 “always-on” 또는 runaway persistence 쪽 문제로 옮겨 갔다는 점이다.

사용자는 이 현상을 보고 “한계를 더 늘려 볼까”라고 물었지만, assistant는 더 큰 ceiling이 해결책이 아니라 “현재 순수 baseline이 과흥분 상태임을 보여주는 증거”라고 해석했다.

### 4.13.12 자동 최적화 도구 구축

사용자는 결국 “한번에 파라미터를 자동으로 최적화해 주는 것”이 필요하다고 판단했다. 조건은 분명했다.

- 그래프와 데이터가 같이 나와야 한다
- 진행률과 ETA가 보여야 한다
- 논문 쓰기에 도움이 되는 형태여야 한다

이에 따라 assistant는 새 도구를 붙였다.

- `v3/scripts/optimize_branch_dynamics.py`

이 도구는 단순히 branch 길이만 보지 않고, 다음 요소를 함께 보게 설계됐다.

- `len1_ratio`
- `hit_max_ticks_ratio`
- `mean_first_active_tick`
- `mean_active_window_ticks`
- `mean_branch_len`

이 단계부터 연구는 “수동 파라미터 조정”에서 “자동 탐색 + 균형 점수 해석”으로 바뀌었다.

### 4.13.13 Windows 멀티프로세스 문제와 실행 안정성 수정

optimizer를 실제로 돌리자, 모델 문제와 별개로 실행기 문제가 터졌다.

- `BrokenProcessPool`
- `handle is closed`
- config마다 `ProcessPoolExecutor`를 반복 생성/종료할 때 생기는 Windows 쪽 불안정성

assistant는 이 문제를 결과 해석 문제가 아니라 실행 안정성 문제로 분리해 고쳤다.

- 동적 import를 일반 import로 변경
- 진행 상황을 중간 저장
- `--resume` 지원
- config 하나가 끝날 때마다 summary/details/progress 저장

이 수정은 “연구가 실패했다”와 “실험기가 실패했다”를 구분하게 해 준 중요한 운영 개선이었다.

### 4.13.14 full60 결과와 trace 분석 전환

optimizer를 돌려도 어떤 config는 늦게 켜지고, 어떤 config는 너무 오래 유지되며, 단순 파라미터만으로는 균형점을 찾기 어렵다는 패턴이 반복됐다. 이때 assistant는 broad sweep만 반복할 게 아니라, 실제 tick-level trace를 보자고 제안했다.

이에 따라 새 도구가 등장한다.

- `v3/scripts/analyze_branch_traces.py`

이 도구의 목적은 다음과 같았다.

- optimizer 결과에서 baseline과 대표 실패 후보를 자동 선정
- config별 tick 평균 곡선 생성
- 대표 샘플 trace 생성
- 비교표, 차이표, 리포트 생성

이것은 연구 초점이 “어느 숫자가 더 낫냐”에서 “어디서 어떤 메커니즘이 병목을 만드는가”로 옮겨 갔음을 뜻한다.

### 4.13.15 구조 수정 후보: 초기 excitability, fatigue, homeostasis

trace 결과를 바탕으로 assistant는 이제 파라미터 조정만으로는 부족하다고 보았다. 그래서 최소한의 메커니즘 추가 후보를 생각하기 시작했다.

대표 후보는 다음과 같았다.

- 입력-정렬 기반 초기 excitability
- 반복 발화 피로(fatigue)
- 출력 포화(saturating fire)
- homeostasis 계열 메커니즘

assistant는 특히 “late ignition + runaway persistence”를 동시에 겨냥하는 방향으로,

- 빠른 점화를 돕되
- 한 번 켜진 것이 끝까지 포화 상태로 가는 것을 막는

구조를 찾으려 했다.

사용자는 이 지점에서도 일관되게 “과도한 보정이 아니라 뉴런/시냅스 쪽 원리로 설명 가능한 수정”을 선호했다.

### 이 대형 세션이 연구에 남긴 가장 큰 변화

이 세션 이전의 EmoNet 연구는 크게 보면 다음 질문 위주였다.

- 구현이 되는가
- 논문을 쓸 수 있는가
- 산출물을 모을 수 있는가

이 세션 이후의 EmoNet 연구는 다음 질문으로 바뀌었다.

- 왜 감정 동역학이 충분히 깊고 설득력 있게 형성되지 않는가
- 어떤 메커니즘이 늦은 점화와 과도한 지속성을 만들고 있는가
- 과도한 프롬프트 보정 없이, 구조적으로 더 나은 감정 흐름을 만들 수 있는가

즉, 이 대형 세션이야말로 EmoNet을 “문서화된 프로젝트”에서 “실제 연구 문제를 가진 시스템”으로 바꿔 놓은 중심축이었다.

## 5. 세션을 가로질러 반복된 핵심 논점

### 5.1 감정의 위치는 입력 텍스트가 아니라 `z` 또는 `z/history`인가

이 질문은 3월 27일 세션에서 가장 명확하게 드러났고, 이후 여러 문서와 실험 판단의 기준이 되었다.

- 입력 텍스트는 자극이다.
- 감정 엔진은 내부 상태를 만든다.
- LLM은 그 상태를 해석하고 표현해야 한다.

이 원칙이 흐려질 때마다 사용자는 “그건 그냥 입력으로부터 다시 응답을 수정하는 것 아니냐”고 되물었다.

### 5.2 softening bias는 단순 문체 문제가 아니라 구조 문제인가

3월 28일부터 반복된 이 논점은, 결국 prompt 설계와 internal state 활용 방식이 얽힌 구조 문제로 정리됐다.

- 제어 신호가 약하면 direct baseline보다 못해진다.
- 제어 신호가 너무 크면 평균화되고 부드러워진다.
- EmoNet의 내부 상태가 실제로 응답에 반영되는 전달 경로가 정교해야 한다.

### 5.3 branch collapse와 late ignition은 연구 전체의 가장 끈질긴 병목이었다

처음에는 branch 길이 1이 많다는 현상으로만 드러났지만, 연구가 진행될수록 더 정교하게 해석됐다.

- early collapse
- late ignition
- no convergence
- runaway persistence

즉, 단순히 “짧다/길다”의 문제가 아니라, 언제 켜지고 언제 꺼지며 얼마나 선택적으로 유지되는가의 문제로 바뀌었다.

### 5.4 연구 운영 문제도 연구 자체만큼 중요했다

이 히스토리에서 눈에 띄는 점 하나는, 연구 성과의 상당 부분이 실행 환경 정리와 직결되어 있었다는 점이다.

- 로컬과 RDP의 경로 차이
- `cmd.exe`와 PowerShell 문법 차이
- 원격 저장소 버전 불일치
- shard, flush, resume 필요성
- Windows 멀티프로세스 이슈

즉, EmoNet 연구는 모델 설계만의 문제가 아니라 장시간 실험을 안정적으로 굴리는 운영 체계 문제이기도 했다.

### 5.5 논문화는 부차 작업이 아니라 연구를 다시 정렬하는 장치였다

논문 개요, fresh draft, audit, worklist, migration 문서는 단순한 글쓰기 산출물이 아니었다.

- 무엇을 실제로 주장할 수 있는지
- 어떤 수치가 current result인지
- 어떤 표가 아직 비어 있는지
- legacy와 active 결과를 어떻게 분리할지

를 정리하는 장치였고, 결과적으로 연구 방향을 다시 조정하는 역할을 했다.

### 문서 측면

- 논문 개요 초안
- 기술 본문 초안

- branch collapse 문제를 독립 변수로 연구하기 시작했다.
- optimizer와 trace analyzer가 들어오면서, EmoNet 연구가 단순 구현 점검을 넘어서 동역학 연구로 확장됐다.

## 7. 아직 닫히지 않은 질문

이 일지 기준으로 보면, 연구는 많은 진척이 있었지만 아래 질문은 여전히 완전히 닫히지 않았다.

1. `z` 또는 `z/history`를 LLM에 어떻게 전달해야 감정이 과도하게 평균화되지 않으면서도 안정적으로 반영되는가
2. `s`는 꼭 필요한 중간 단계인가, 아니면 일부 실험에서는 `z/history -> LLM` 직접 연결이 더 타당한가
3. branch dynamics에서 가장 핵심적인 병목은 정확히 무엇인가
4. 과도한 보정 없이도 설득력 있는 감정 흐름을 만들 수 있는 최소 메커니즘은 무엇인가
5. 논문에서 어디까지를 “현재 결과”로, 어디까지를 “후속 과제”로 적어야 가장 정직하고 강한가

## 8. 최종 정리

이번 채팅 히스토리를 연구 일지로 다시 읽어 보면, EmoNet은 단순히 감정 응답 시스템을 만드는 프로젝트가 아니었다. 대화가 반복될수록 문제는 점점 더 안쪽으로 들어갔다.

- 감정은 어디에 존재하는가
- 내부 상태를 어떻게 외부 표현으로 바꾸는가
- 왜 branch는 금방 죽거나 너무 오래 살아남는가
- 보정을 줄이면서도 구조적 설명력을 어떻게 높일 수 있는가

즉, 연구의 초점은 “잘 되는 데모를 만들기”에서 “감정 동역학을 설계하고 이해하기”로 이동했다. 그 이동 경로가 이 히스토리 전체에 아주 선명하게 남아 있다.
